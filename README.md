# 業務管理システム デモ (MVP)

顧客・案件・タスク・対応履歴を **ひとつの画面体系で一元管理** するための業務管理システムのデモ版です。

このデモは画面の見本ではなく、**実際の業務管理システムへそのまま発展させることを前提に設計した「動作する MVP」** です。
データ構造・権限・変更履歴・CSV 移行・ファイル管理まで、実運用で必要になる土台を一貫した考え方で組み込んでいます。

---

## 1. このデモが解決したい課題

| 現状の課題 (Excel / スプレッドシート運用) | このシステムでの解決 |
| --- | --- |
| 情報が複数のファイル・ツールに分散している | 顧客 → 案件 → タスク → 対応履歴を関連付けて一元管理 |
| 担当者ごとに管理方法が異なる | 全員が同じ画面・同じステータス定義で入力する |
| 案件の進捗状況が把握しにくい | ダッシュボードで進行中・確認待ち・期限超過を一目で確認。数字をクリックすると該当一覧へ |
| 対応履歴を追いにくい | 顧客・案件ごとに電話・メール・訪問の記録を時系列で表示 |
| 担当者変更時の引き継ぎに時間がかかる | 担当者を変えても、過去の対応履歴・変更履歴・ファイルは案件に残り続ける |
| タスクや期限の確認が難しい | 期限超過・本日期限・期限間近を色分けし、担当者別に絞り込める |
| 必要な情報の検索に時間がかかる | 案件名・顧客・担当者・ステータス・優先度・期限を組み合わせて即時に絞り込み |
| 誰がどの情報を変更したのか分からない | すべての変更を監査ログに「誰が・いつ・何を・どう変えたか」で記録 |

## 2. 起動方法

必要なもの: **Node.js 20 以上** (推奨 22 以上)。データベースはファイル型 (SQLite) のため別途インストール不要です。

```bash
npm install          # 依存ライブラリの取得
npm run setup        # .env 作成 → DB 作成 → サンプルデータ投入
npm run dev          # 開発サーバー起動
```

ブラウザで <http://localhost:3000> を開きます。

その他のコマンド:

| コマンド | 内容 |
| --- | --- |
| `npm run db:seed` | サンプルデータを初期状態に戻す (設定画面の「デモデータを初期化」と同じ) |
| `npm run build` / `npm start` | 本番ビルドと起動 |
| `npm test` | 単体テスト (権限・CSV・入力検証・監査ログ差分・AI候補生成) |
| `npm run typecheck` / `npm run lint` | 型チェック / 静的解析 |

## 4. おすすめの確認シナリオ

1. **管理者でログイン → ダッシュボード → 「期限超過タスク」をクリック → タスク一覧 → 案件詳細 → 対応履歴タブ**
   問題のあるタスクから案件の経緯まで、クリックだけで辿れます。
2. **顧客一覧 → 「さくら」で検索 → 顧客詳細 → 関連案件 → 案件詳細 → タスクタブ**
   顧客を起点に、その顧客に関するすべての情報を追えます。
3. **案件詳細 → 「現在の状態」で担当者・ステータスを変更 → 対応履歴を登録 → 変更履歴タブ / 監査ログ**
   変更した内容が「誰が・いつ・何を・どう変えたか」の形で記録されます。
4. **一般ユーザー (田中 花子) に切替 → 管理者メニューが消え、`/admin/users` を直接開くと 403 → ダッシュボードは「自分の担当」中心**
   権限による画面・操作の制御を確認できます。
5. **案件一覧 → ステータス「進行中」+ 優先度「高」で絞り込み → CSV エクスポート**
   絞り込んだ条件のまま Excel で開ける CSV を出力します。
6. **CSV 取込 (管理者) → 顧客 CSV を検証 → エラー行を確認 → 登録**
   既存の Excel データを移行するときの流れです。必須項目・形式・重複・担当者の存在をチェックします。
7. **案件詳細 → 「AI支援」→ タスク候補を生成 → 内容を編集して承認**
   AI は候補を出すだけで、承認したものだけが登録されます (Human-in-the-loop)。

## 5. 主要機能

| 画面 | できること |
| --- | --- |
| **ダッシュボード** | 案件総数 / 進行中 / 完了 / 期限超過タスク / 本日期限 / 未対応・確認待ち、ステータス別・担当者別の案件状況、至急対応タスク、最近更新された案件、最近の対応履歴。すべて該当一覧へリンク。「自分の担当」と「全体」を切替 |
| **顧客・取引先** | 一覧 (検索・ステータス・社内担当で絞り込み)、登録・編集・削除、詳細 (基本情報・連絡先・関連案件・未完了タスク・対応履歴・引き継ぎメモ) |
| **案件・プロジェクト** | 一覧 (案件名・顧客・担当者・ステータス・優先度・期限・期限超過・自分の担当で絞り込み、並び替え)、登録・編集・削除、詳細 (状態のインライン更新、次にすべきこと、タスク / 対応履歴 / ファイル / 変更履歴タブ、AI支援) |
| **タスク** | 案件横断の一覧 (期限超過・本日・間近のクイック絞り込み、担当者・ステータス・優先度・期限)、登録・編集・削除、一覧上でのステータス変更 |
| **対応履歴** | 電話 / メール / 訪問 / オンライン会議 / 社内対応 / その他を時系列で記録。顧客・対応者・種別・期間で絞り込み |
| **ファイル** | 見積書 / 契約書 / 提案資料 / その他を案件に紐づけて保存・ダウンロード・削除 |
| **ユーザー管理** (管理者) | ユーザーの登録・編集、権限 (管理者 / 一般)、有効・無効、最終ログイン |
| **監査ログ** (管理者) | 日時・ユーザー・操作・対象・変更内容 (変更前 → 変更後)。ユーザー・対象・操作・期間で絞り込み |
| **CSV取込** (管理者) | 顧客 / 案件 / タスクの一括登録。検証 → エラー行の確認 → 登録の 3 ステップ |
| **設定** (管理者) | 組織名、期限間近とみなす日数、システム情報、デモデータの初期化 |

すべての一覧で **CSV エクスポート** (絞り込み条件を反映) ができます。

## 6. データの考え方

```
ユーザー (User)
  └ 顧客 (Customer) ── 社内担当者
       └ 案件 (Project) ── 担当者・ステータス・優先度・進捗率・期限
            ├ タスク (Task) ── 担当者・ステータス・優先度・期限
            ├ 対応履歴 (Activity) ── 対応者・種別・日時・内容
            ├ ファイル (ProjectFile) ── 分類・保存先
            └ 変更履歴 (AuditLog) ── 誰が・いつ・何を・どう変えたか
```

- 担当者は氏名の文字列ではなく **ユーザー ID で関連付け** ます。氏名変更・退職があっても過去データが壊れません。
- 対応履歴は顧客に必ず紐づき、案件には任意で紐づきます。案件を削除しても顧客側の対応履歴は残ります。
- ファイルは「業務データ (メタ情報)」と「ファイル実体」を分離して保存します。将来クラウドストレージへ切り替えても画面は変わりません。
- 監査ログは削除されたデータの名前も保持するため、削除後も「何が削除されたか」を追えます。

詳細は [docs/DESIGN.md](docs/DESIGN.md) を参照してください。

## 7. 権限の考え方

| 機能 | 管理者 | 一般ユーザー |
| --- | --- | --- |
| 顧客・案件・タスク・対応履歴・ファイルの閲覧 | ○ | ○ (全件) |
| 顧客・案件・タスク・対応履歴の登録 | ○ | ○ |
| 顧客の編集 | ○ | 社内担当者のみ |
| 案件の編集・状態変更 | ○ | 案件の担当者のみ |
| タスクの編集 | ○ | タスク担当者 / 作成者 / 案件担当者 |
| 対応履歴の編集・削除 | ○ | 本人の記録のみ |
| 顧客・案件の削除 | ○ | × |
| CSV エクスポート | ○ | ○ |
| CSV 取込・ユーザー管理・監査ログ・設定 | ○ | × |

「情報は全員で共有し、変更は責任者に限定する」方針です。画面のボタン表示と API の権限チェックは同じルール定義を使っているため、URL を直接叩いても操作できません。

## 9. Vercel へのデプロイ (GitHub 連携)

このデモは **Vercel + PostgreSQL** でそのまま動作します。ローカルの SQLite / ローカルディスク保存は、デプロイ時に自動で PostgreSQL / DB 内ファイル保存へ切り替わります (コード変更不要)。

### 手順

1. **GitHub にプッシュ**
   ```bash
   git init -b main
   git add .
   git commit -m "業務管理システム デモ 初版"
   # GitHub で空のリポジトリを作成してから
   git remote add origin https://github.com/<your-account>/<repo>.git
   git push -u origin main
   ```
   `.env`、`prisma/dev.db`、`storage/` は `.gitignore` 済みで、リポジトリには含まれません。

2. **Vercel でプロジェクトを作成**
   [vercel.com/new](https://vercel.com/new) → GitHub リポジトリを Import → 設定はそのまま Deploy。
   ビルドコマンドは `vercel.json` で `node scripts/vercel-build.mjs` に固定されています (マイグレーション → 初回のみサンプルデータ投入 → ビルド)。
   ※ この時点ではデータベースが無いためビルドは失敗します。次の手順で接続してください。

3. **PostgreSQL を接続** (プロジェクトの *Storage* タブ → *Create Database* → **Prisma Postgres** または **Neon** (どちらも無料枠あり) を選択 → Connect)
   接続文字列の環境変数が自動で追加されます (Prisma Postgres は `PRISMA_DATABASE_URL` と `POSTGRES_URL`、Neon は `DATABASE_URL` と `DATABASE_URL_UNPOOLED`)。ビルドスクリプトがこれらを自動検出するため、手動で `DATABASE_URL` を作る必要はありません。リージョンは Vercel の Functions リージョン (`vercel.json` では東京 `hnd1`) に近いものを選ぶと応答が速くなります。
   Neon 以外 (Supabase / Vercel Postgres / 任意の PostgreSQL) でも、`DATABASE_URL` (接続文字列) を環境変数に設定すれば動作します。

4. **再デプロイ** (*Deployments* → 最新のデプロイ → *Redeploy*)
   ビルドログに「サンプルデータを投入します」と表示されれば完了です。発行された URL を開き、`admin@example.com` / `password123` でログインしてください。

### 環境変数

| 変数 | 必須 | 説明 |
| --- | --- | --- |
| `DATABASE_URL` | ○ | PostgreSQL の接続文字列。Storage 連携が別名で設定する場合 (Prisma Postgres: `PRISMA_DATABASE_URL` / `POSTGRES_URL`、Supabase: `POSTGRES_PRISMA_URL` 等) も自動で検出します。`prisma+postgres://` 形式 (Prisma Postgres) と `postgres://` 形式のどちらも可 |
| `DIRECT_URL` | – | マイグレーション用の直接接続。未設定なら `DATABASE_URL_UNPOOLED` → `POSTGRES_URL_NON_POOLING` → `DATABASE_URL` の順に自動で使用 |
| `FILE_STORAGE_PROVIDER` | – | 未設定時は Vercel 上で自動的に `database` (DB 内保存)。S3 等を使う場合は Provider を追加して指定 |
| `ANTHROPIC_API_KEY` | – | 設定すると AI 支援が Claude による生成に切り替わります |
| `SEED_ON_BUILD` | – | `0` にするとビルド時のサンプルデータ投入を行いません |

### 運用上の注意

- **デモ用の公開設定です。** ログイン画面にアカウント一覧が表示され、パスワードも共通です。URL を渡す相手を限定し、不要になったら Vercel の *Deployment Protection* (パスワード保護 / Vercel 認証) を有効にするか、プロジェクトを削除してください。
- 誰かがデータを変更しても、管理者でログイン → 設定 → **デモデータを初期化** で元に戻せます。
- サンプルデータは初回ビルド時のみ投入されます (DB が空のときだけ)。再デプロイでデータが消えることはありません。
- データモデルを変更した場合は、`prisma/postgres/migrations` にも PostgreSQL 用のマイグレーションを追加してください (詳細は `docs/DESIGN.md`)。
